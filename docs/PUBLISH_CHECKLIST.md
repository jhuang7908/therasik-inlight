# InLight 发布前审计清单

每次发布（每周更新、补发、改稿）之前都要跑完这份清单。**全部通过才能发布。** 有一项不过就不发，先改，改完从头再跑。

- 自动项：由 `tools/audit_weekly.py` 判定，报告里有同一编号。
- 人工项：报告里列为 MANUAL，发布人逐条确认后在 PR 描述里勾选。
- 结果分五种：FAIL 拦发布；WARN 要人工看过并在 PR 里写明结论；LEGACY 是已登记的历史问题（只针对已发布的旧条目，见文末）；MANUAL 是人工项；PASS 通过。
- 规则来源：`AUTOMATION.md`「写作规则」、`run_weekly.py` 写作提示词、`docs/number_check.md`、`docs/author_check.md`、`docs/source_audit.md`、`tests/test_r8_golive.py`，以及 `inlight_review` 下的文章规范（article_spec / writing_standard / 质控说明）、`house_style_v3`、`inlight_blue_light`，再加上用户的发布规则。

## 发布流程

1. 抓候选（不需要密钥）：`bash weekly.sh --fetch-only`，候选写在 `preview/weekly/<周>/candidates.json`。
2. 从候选里选题、写稿，放进 `content/weekly/<周>/`（`articles.json`、`deals.json`、`images/`），合并到 `content/latest.json`；精编文章则写 `content/articles/<id>.json/.md` 和 `content/catalog.json`。
3. 生成页面：`python build_pages.py`。
4. 审计：
   ```bash
   python tools/audit_weekly.py --base origin/main --week content/weekly/<周> \
       --candidates preview/weekly/<周>/candidates.json --run-tests
   ```
   报告在 `preview/audit/<时间>/audit_report.md` 和 `.json`，退出码 0 才算通过。
5. 逐条确认人工项和全部 WARN，在 PR 描述里写明。
6. 出补丁或 PR，合入 `main`。
7. 上线后核验：`python tools/audit_weekly.py --base <上一版> --live https://inlight.therasik.com --offline`，再做一遍 J5 人工目检。

注意：`tests/test_r8_golive.py` 把精编文章数固定为 36，并锁定首页 DEALS 区块的哈希和 22 条的条数。往 `catalog.json` 增加精编文章或改动 `index.html` 里的 DEALS 时，这两个测试一定会失败。要在同一个提交里有意更新这两个期望值，并在 PR 里说明。只走 `content/latest.json` 的周更不会碰到这两个测试。

## 历史问题基线

`tools/audit_baseline.json` 登记了现有已发布内容的遗留问题（2026-10-11 校准，共 36 条）。这些条目报 LEGACY，不拦发布：

- B1：c1-org-5、c2-ai-5、c3-io-2、c5-am-7、c6-ab-4 共 5 篇。速览里有数字已在 `docs/source_audit.md` 对原文核对过，但正文和数据卡里没写。
- D4：c4-ai-8、c4-ai-9、c5-am-7、c5-am-8、c6-ab-7、c6-ab-8、c6-ab-9、c9-rna-7、c9-rna-9 共 9 篇，有超过 150 字的段落。
- E4：c5-am-9 的机制图没检出赤陶红强调色。
- E5：17 张机制图是纯白底，不是暖米白；另有 2 张经济动态图底色偏离（Boehringer–Prime 一张是浅蓝底，SEC 公告那条是灰白底）。
- E6：c6-ab-4、c6-ab-5 的卡片图纸纹颗粒偏弱。

规则：

1. 基线只对已发布的旧条目生效，新条目一律不吃基线。
2. 修好一条就从基线里删掉一条。
3. 不要为了让新内容通过而重写基线；只有校准时才用 `--write-baseline`。
